# C 台放置失败：控制链路诊断报告

**日期**：2026-09-13
**状态**：诊断完成（read-only），未修改任何默认行为
**诊断脚本**：`scripts/diagnose_c_placement.py`（新增，只读）

> **本轮目标**：回答"到底是哪一层坏了"，而不是"再试一次能不能成功"。
> **结论**：不是策略精度极限。是**两层缺陷叠加**：控制器发出的 ω 只兑现约 1/6，且规划器的 −0.08 m 硬编码偏移把目标推出可行窗口。

## 一、结论先行

| 层 | 缺陷 | 证据 | 严重度 |
|---|---|---|---|
| **规划层** | `mujoco.py:374` 把选定的站位硬推 −0.08 m | 窗口只有 0.08 m 宽，这一步正好推到近边界外 → B/C 双双 `BILATERAL_REACH` | 🔴 高（确定性 bug） |
| **执行层** | 策略对 `ω` 的跟踪严重不足（约 16× 欠额） | 命令 `ω=0.112` 持续 **34 秒**，yaw 纹丝不动在 −6.41° | 🔴 高（真凶） |
| **控制层** | `hold_command` 的 slew 限幅约 0.0016/tick | 爬升到 0.1745 需 ~0.44 s 仿真时间 | 🟡 中（非致命） |
| **站位搜索** | 只在到达朝向下搜 x,y，不搜朝向 | C 窗口：yaw 0°=9 个可行、±10°=2~3、±15°=0 | 🟡 中（真实约束） |

**关键更正**（推翻之前文档结论）：

- ❌ 旧结论"策略几乎不能原地转体（0.08°/s）" → ✅ 实测策略**能**转，ω=0.3 时可达 **2.0–2.2°/s**（README 里的 0.08°/s 是**在错误控制输入下**测出来的，不是策略能力）。
- ❌ 旧结论"reach 窗口 0.14 m" → ✅ 端点跨度 **0.12 m**（0.22–0.34）；0.14 是加了采样步长。
- ❌ 旧结论"几何矛盾不可解" → 早已撤回，本轮再次确认**不成立**。

## 二、逐项证据

### 2.1 规划层的 −0.08 m 偏移（确定性 bug）

`skills/mujoco.py:374`：

```python
final_xy = np.asarray(selected["xy"]) - np.array([0.08, 0.0])
```

站位规划器算出**可达**站位后，代码又把它往 −x 推 0.08 m。实测：

| 台 | 可行窗口 x | 规划器选中 | 偏移后 | 偏移后可行？ |
|---|---|---|---|---|
| B | [0.910, 0.990] | 0.950（窗口内部 ✅） | 0.870 | ❌ `BILATERAL_REACH` |
| C | [1.280, 1.360] | 1.320（窗口内部 ✅） | 1.240 | ❌ `BILATERAL_REACH` |

**窗口宽 0.08 m，偏移正好 0.08 m** —— 每次都精准落到近边界外侧。
B 台能过只是因为到达误差恰好把落点拉回窗内；C 台不行。

### 2.2 策略 ω 跟踪不足（真凶）

**直发速度命令测试**（绕开位置环，三种手臂/负载状态）：

| 状态 | cmd=(0,0,+0.3) 的 dyaw | cmd=(0,0,−0.3) 的 dyaw |
|---|---|---|
| 空手默认姿态 | +3.99° / 2s | −4.44° / 2s |
| 搬运手臂姿态 | +4.17° / 2s | −4.66° / 2s |
| 持物 | +4.18° / 2s | −4.14° / 2s |

→ **三种状态一致，能转。手臂姿态与负载都不是瓶颈。**

**ω 跟踪曲线（稳态）**：

| 命令 ω (rad/s) | 实际达成 | 达成率 |
|---|---|---|
| 0.05 | 0.108 °/s | |
| 0.10 | 0.280 °/s | |
| 0.15 | 0.529 °/s | |
| 0.20 | 0.824 °/s | |
| 0.25 | 1.140 °/s | |
| 0.30 | 1.493 °/s | 0.087 (°/s per rad/s) |

命令 0.1745 rad/s（=10°/s）→ 实得 **0.62 °/s**。**约 16× 欠额，且次线性饱和。**

**真实运行 trace 的终局证据**（`diag-trace` C 台）：

```
t=61.612  req_w=+0.1118  eff_w=+0.1118  yaw=-6.41  x=1.3766
t=61.650  req_w=+0.1120  eff_w=+0.1120  yaw=-6.42  x=1.3757
```

`req_w == eff_w`（**命令确实传到了策略**），但 yaw 冻结在 −6.41°。
全程 **13167 / 30825 tick（约 34 秒）** 有 `|ω|>0.05`，平均 0.108 rad/s
→ 按跟踪曲线只应产出约 0.6°/s × 34s ≈ 20°，实际产出 **≈0.01°**。

> 注：`req_omega_saturated_frac = 0.0`，即 ±0.3 的限幅从未触发；slew 限幅最终也放行了。
> **所以既不是限幅问题，也不是"命令没传到"。就是策略在低速 ω 上几乎不响应。**

### 2.3 站位搜索不含朝向

`stance.py:132` `evaluate()` 只设 `qpos[:2]`，**从不改 `qpos[3:7]`**；
且每次调用都 `qpos[:] = self.original`（构造时的快照）——所以朝向完全固定。

扫描朝向（每个 yaw 重建 planner，让快照带上朝向）：

| yaw | B 可行数 | B 窗口 | C 可行数 | C 窗口 |
|---|---|---|---|---|
| 0° | 9 | 0.080 m | 9 | 0.080 m |
| ±5° | 9 / 9 | 0.080 m | 8 / 9 | 0.080 / 0.080 |
| ±10° | 3 / 3 | 0.000 m | 2 / 3 | 0.000 / 0.000 |
| ±15° | 3 / 3 | 0.000 m | 0 / 3 | — |
| ±20° | 0 / 0 | — | 0 / 0 | — |

→ 朝向敏感性**真实存在**（±10° 就塌），但这是**搜索空间不含朝向**造成的，不是手臂物理极限。
→ B 与 C 基本一致；B 在高 yaw 下甚至更差。**"侧向偏移破坏可达性"的旧结论不成立。**
