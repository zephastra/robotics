# 010 架构与数据边界（设计）

## 1. 分层

```text
订单输入（JSON/YAML；语言入口后续可选）
                  ↓
任务编排/调度 ── 订单、库存、托盘账本（单写者）
                  ↓
资源预约/交接事务/设备技能接口
                  ↓
人形适配器 | 机械臂适配器 | AMR/Nav2适配器 | 输送设备适配器
                  ↓
本地互锁与最终命令门
                  ↓
统一物理世界（接触、货物、设备、时间）

传感器→感知/定位→有来源和年龄的观测→控制/任务
仿真真值→独立验收器→报告（禁止反向控制）
```

## 2. 关键所有权

- 仿真步进者：唯一时钟/物理状态写者；UI、LLM 和调度不直接改 qpos/物体位姿。
- 订单服务：任务状态和货物账本单写者，SQLite 事务同时保存事件。
- 每设备适配器：一个有效 command generation，接受技能请求并返回反馈，非阻塞。
- 每执行链最终安全门：唯一最终命令发布者。Nav2 的恢复和平滑器也必须经过它。
- 交接事务协调者：串行管理两设备和接驳位资源；不凭“发送了启动”宣布货物转移。
- 独立验收器：只读真值/接触/日志，不能给控制器提供校正目标。

## 3. 坐标与时间

- 全场静态 `map`、各 AMR 独立 odom/base/sensor frame，设备名称唯一，不重复 TF 发布者。
- 物理世界与 map 变换在部署校准冻结；不可把仿真坐标直接混作相机观测。
- 相机内外参、点云 frame、单位、时间戳都写入观测。机械臂 base 与工作站 frame 可追溯。
- 唯一 `/clock`。物理/服务/能耗用 sim；消息过期、进程存活与许可用本地 monotonic wall。
- 暂停/时间重置必须显式传播，旧控制命令/许可不能在恢复后直接重放。

## 4. 资源设计

首版资源至少有：人形/机械臂共享上料区、取盘区、输送带段、输送末端、AMR停靠区、接收站及双托盘缓冲位、窄道。充电位为扩展预留，V1 不要求自动充电闭环。
人形和机械臂先采用共享上料区互斥，不在同一托盘旁同时伸手。
接驳需原子获得“发货端+接收端+对接区”，不得占一个资源无限等待另一个。
运输途中不持有已清空上料站；站点释放需实测清空，不是定时 sleep。
V1 限定任务图避免环形多资源等待；不宣称任意工厂拓扑无死锁。

## 5. 输送接触模型

候选：真实滚筒/运动表面，或明确建模且仅作用于实际接触物体的有界切向牵引。
P1 检查停止、侧向滑移、间隙跨越、误停靠拒绝。记录支撑与接触力来源。
不能通过强制设置托盘速度、位置或与 AMR 隐藏绑定得到“可靠运输”。
车载托盘保持机构必须有可检查的物理约束设计（挡边/机械止挡等），不能用隐形 weld。

## 6. 初期与未来

V1 用结构化订单和确定性编排；不依赖 LLM。后续语言模型只能提出相同订单/技能请求。
高层协议尽量本体中立，但新设备的 footprint、停止能力、可达范围与技能需要重新标定。
只读展示面板从实际事件生成，不负责时序驱动机器人。
