## 0. 先读这页：目标、当前卡点、禁止事项

### 0.1 我们最终要交付什么

在一个连续的共同物理世界中，收到一个结构化订单后：

1. 人形机器人从真实有限库存取得空托盘并送到供盘位置。
2. 固定机械臂通过相机实际观察零件，抓取订单需要的数量并装盘。
3. 输送机构把托盘交给指定 AMR；发生实际物权交接。
4. AMR 用真实 Nav2 路径执行到接收工位；载荷不能掉落，不能偷偷固定。
5. 输送、卸盘、接收缓冲区完成实际接收。
6. 独立验收器核对实际托盘、零件、数量、位置、订单身份与安全结果。
7. 第二台 AMR、多订单、有限库存、竞争和规定故障也有证据。

V1 本体为：一个人形、一个固定机械臂、两台带运输甲板的 AMR、源端输送和具有双托盘容量的接收区。不是复杂加工、复杂装配、通用家庭整理，也不是无限循环生产线。

### 0.2 当前不能直接冲最终长链

当前关键瓶颈是**带自由载荷的运输资格**，不是“缺一个总启动脚本”。最新 v7 铰接保持机构只证明了静止闭合、接触、释放、视觉与停止；尚未证明运动中可靠保持。

先完成：保持机构运行契约 → 甲板偏航诊断 → 新候选世界集成资格 → 初始化载荷的短程真实 Nav2 → 连续交接与卸盘。通过这些门后，才进入完整订单、第二台车和车队。

## 4. G1：先把保持机构变成可监督的技能

### 4.1 当前问题

`probe_tray_retainer.py --hinged` 是实验探针，不是已集成的运输技能。它的静止报告不能自动给导航权限。

待新增的状态概念可以是：OPEN → CLOSING → CLOSED_VERIFIED → TRANSPORTING → RELEASING → OPEN_VERIFIED；异常进入 FAULT/UNKNOWN。先与已有 schema 对齐，不要未经检查重复造枚举。

### 4.2 必须明确的观察与权限

每次观察至少带：车辆/机构身份、左右关节位置与速度、接触存在与支持来源、接触力及单位、观测时刻/年龄、命令 epoch、运行身份。机械位置达到关闭值不等于托盘被双侧真实保持。

候选力/时长判据必须说明来源；优先复用已有接受标准。新诊断阈值不能偷换原运输 5 mm 滑移或甲板姿态门。

运输许可要求：视觉确认载荷有效且新鲜，车辆实际静止，装载已提交，双方接触/姿态门满足，H/臂退出共享区，释放执行器状态正确，安全守卫在线。必须综合许可，而不是某个接触布尔值独自控制车轮。

### 4.3 权限边界

- 执行器只作用于真实铰链，保留可见几何与限力。
- MuJoCo 接触可作为**明确声明的理想触觉**，不能读取 cargo 真值姿态去代替视觉定位。
- 独立真值评估器可读载荷姿态，但它的结果不回流控制器。
- 释放只在实际停车且接收许可有效时执行；释放失败不能启动卸盘。
- 运动中支持 UNKNOWN/观察过期：执行阶段相关的受控停止；不能自动开鞋、抛弃载荷或结束 custody。

### 4.4 最小测试集

先纯测试：状态跳转、观察失效、单侧接触、错误车辆 ID、旧 epoch 回调、闭合超时、释放超时、取消与重复命令。

再小物理测试：当前静止正例、保持释放位负例、**初始视觉遮挡 UNKNOWN**、单側保持缺失、释放不能完成。最后两项需明确故障注入方式，不把改目标指令冒充实体卡死。

验收：每个反例都不给运输授权；所有失败可辨识；没有将 UNKNOWN 记为 PASS；失效路径不篡改 cargo；原正常静止用例不回归。未测分支明确 NOT_RUN。

## 5. G2：把三个根因拆开，停止混合调参

### 5.1 需要分别解释的三件事

1. 2 ms 单步接触缺失如何影响支持状态判定？
2. 托盘相对甲板为何滑移超过 5 mm？
3. 甲板 `c_deck_yaw` 为何超过 ±0.01 rad？

这三者不是同一个“跳盘”。其中 `c_deck_yaw` 是甲板相对车体的机械自由度，不是车辆 map 坐标偏航；不能把机器人转弯本身判成甲板失效。

### 5.2 记录什么

在同一 physics tick 对齐：车轮目标/实际速度、甲板关节位移速度、执行器控制、保持鞋位置/速度/接触力、支持接触、载荷相对滑移（只给独立评估器）、姿态门原因、导航命令及其年龄、停止命令和物理停止时刻。

必要时记录约束/被动力/力矩与模型定义，说明坐标系、单位、采样在 step 前后。接触几何缓存的时间可为当前 t−dt，不能拿错 tick 解释因果。

`deck_support_forensics.py` 已有分析；原始 `mj_geomDistance` 有未经资格确认的异常负值，不能作为精确穿透事实。解析下平面界也不是任意凸体精确距离。报告应保留这些工具的适用范围。

### 5.3 小实验顺序

先静止空甲板/带载甲板；再保持机构关闭带载短直行；最后短转弯或必要的接收腿。一次只改变一个因素，对比相同版本、相同初态和相同任务。

当前被动甲板 yaw 刚度/阻尼约 40/8，物理范围 ±0.05 rad、运输资格 ±0.01 rad；侧移刚度/阻尼约 150/5。车载平台前伸很长。它们只是排查线索，不能先宣称根因。

同一假设两次失败且没有新增信息：暂停该假设的长测，写出证伪结果与下一种测量。不要反复跑千秒全链等奇迹。

## 6. G3：根据证据做最小补救

### 6.1 先选分支，不能一起乱改

- 若是命令失效/唯一写入者冲突：修身份、过期处理、状态发布与停车反馈，不改物理。
- 若是有限执行器能力/制动律不够：做有界反馈，测饱和、停车距离和载荷响应。限速不是证明；原门仍要通过。
- 若是甲板被动 yaw 弹性导致运输失格：评估有限扭矩伺服或可释放的机械约束候选。必须声明负载能力、释放、故障路径与实际物理代价。
- 若是支持状态使用瞬时样本不合理：提出有来源的观测契约审查，保留原瞬时结果。未经授权不能删除原失败或偷偷改变冻结判据；滤波不能把持续失联/掉落伪装正常。
- 若真实承载机构不稳定：新机构/安装几何候选单独版本、重新验收。不要用焊接自由载荷、删除被动关节或关闭碰撞解决。

### 6.2 判定修复有效

原正常情况通过；有意失效情况仍会失败；负载停止、滑移、姿态、真实到达分别有结果。禁止为了到达而收紧/放宽任意一项阈值，或只是延长预算掩盖没有进展。

速度 0.08 m/s、multi-CCD 等目前是诊断条件，不自动成为发布默认。若选择新默认，记录适用版本和全部影响回归。

按身份映射增加执行器后的旧控制数组；明确未操作执行器目标，不能数组错位把人形支撑力清零。人形停止任务也应维持安全支撑，不是把全世界 ctrl 归零。

双车最终都要装对应机构并独立审查；第一车 v7 合格不等于第二车合格。

退出门：候选世界整体资格、关键旧链回归、视觉正例/遮挡负例、闭合释放、卸盘清障都通过。仅 STATIC_ONLY 不满足。

## 8. G5：候选世界的导航身份与安全包络

现有导航 profile/配置主要是 v5。不能编辑几处 SHA 后宣称它支持 v7。

为新候选生成独立配置：世界身份、车辆身份、传感器外参、甲板/保持机构几何、允许姿态、载荷外形、导航 footprint、栅格地图与碰撞监控区。对比来源和生成过程可追溯。

参考已有：`make_joint_nav_profile.py`、`nav_geometry_inventory.py`、`transport_posture_gate.py`、`humanoid_posture_permit.py`、`wheel_authority.py`。

保持鞋张开/关闭对足迹的影响必须考虑。二维 Nav2 足迹只能管平面导航，不能取代机械臂、人形、输送部件与载荷的三维互锁。

核实 TF 一致：`map → odom → base → scan`；只有一个 `/clock`、每个必要 TF 边只有一个来源。AMCL 或 SLAM 对 map→odom 的所有权不能重叠。

## 9. G6：先过初始化载荷的短程真实 Nav2

### 9.1 现有命令边界

`probe_vehicle_nav2.py` 当前默认 v5，没有现成 v7 retainer/world 参数；`probe_candidate_multi_loading.py --world` 当前仅 v3/v4/v5。先新增受测的候选选择/机构互锁，再使用。不要写一个不存在的 `--world v7` 命令让操作者试错。

初始化 cargo 只在场景开始允许。这一步是运输隔离实验，不冒充实际 H/臂加载。

### 9.2 测试次序

1. 实际静止、闭合确认、短直行、目标到达、受控停车。
2. 接收方向短腿与必要转弯。
3. 运输中观察/支持故障，确认受控停与 custody 保留。
4. 合法初始扰动/载荷布局，检查是否只对中心样例有效。

原到达、5 mm 滑移、甲板姿态、停车速度/漂移等门全部保留。新增保持与安全门只增加要求。退出码、Nav2 action 成功和物理结果分别记录。

建议先三个独立调试样例检验重复性，不能把它们宣传为可靠性统计，也不能替代最终冻结种子。若第三次失败，保留全部；不要只选最佳一次。

## 10. G7：接上真实加载与卸载

把隔离 Nav2 路径接到实际源端链：H 供盘 → RGB-D/PCL 装盘 → 视觉核数 → 源端到甲板交接 → 实际支持稳定 → 关闭保持鞋 → 资格成立 → Nav2 → 停车 → 接收许可 → 释放确认 → 输送卸盘 → 接收确认。

关键顺序：**不能夹着托盘强行输送；也不能在运动中提前释放。**

使用 `src/workcell/physical_transfer_session.py`、`ledger.py`、`transfer.py`、`resources.py` 的实际接口，先读源码再写适配。不要假设已有某个函数签名。

一盘从头到尾有稳定物理 ID、订单 ID、transfer ID。所有权只能在具有物理证据的 COMMITTED 转移。开始交接即保持 TRANSFERRING/区域占用；中断或证据缺失不得改为 RELEASED、空闲或任务成功。

测试至少包含：源端拒绝、半程停止、夹持未释放、接收忙、卸盘失败。报告“最终在接收区”之外还要核验 ledger 与每次支持/占用证据相符。

## 11. G8：安全与恢复必须在订单前收口

### 11.1 三维守卫

结合声明外参、关节 FK、自状态、导航定位和实际视觉观测，检查允许的姿态/扫掠包络。禁止读 cargo 真值位置作为安全控制输入。

至少覆盖 H/臂共享区、Panda 与托盘/保持鞋、输送交接区、车载伸出部件、接收结构。模型里碰撞后来发生再报错不等于预测性安全守卫；两者必须分开称呼。

### 11.2 中断与恢复

发停止命令 → 保持必要支撑/载荷约束 → 实测停止 → 检查支持、物权和资源状态 → 才接受显式恢复授权。

未知、半转移、接收不可用：NEEDS_ATTENTION，区域保持占用。不能强制释放 lease 后让别的车进入，也不能“重置仿真到上一阶段”当恢复。

安全停止要能反证：断开命令、失去心跳、取消或夹持故障时，确实测到速度/漂移合格；不是日志打印 STOPPED。

`FREEZE_FALLBACK` 等标签不是成功证据。任何直接把整个世界速度清零的兜底不能算物理停止能力。

### 11.3 P4 退出

只有真实视觉装盘、H/臂互锁、运输保持、输送/卸盘、受控停止及有界恢复证据齐全后，才更新 `P4-BELT-03` 状态。不要先写 DONE 再补报告。

## 12. G9：完成第一个真正订单 N01

待新增或补齐的订单驱动器是应用层，不是让实验探针自己打印“订单完成”。入口为受 schema 校验的结构化订单；V1 不需要 LLM。

最少状态：接收/校验 → 库存预留 → 调度/资源预留 → 供盘 → 装盘 → 核数 → 交接 → 运输 → 卸盘 → 独立核验 → 结束。使用现有枚举/事件模型，不要重复造框架。

步骤不能只按固定时间成功。每个技能要有前置、物理完成证据、失败原因、超时、幂等键和阶段相关取消。总订单预算来自测量的阶段预算，不是无限 while。

初版仅 AMR1 正常单订单。全程一个 WorldOwner、一个模型/data、一个时钟、不重置场景、不初始化第二个私有仿真。

出口：订单 SUCCEEDED、实物/数量/目的地/身份 PASS、安全 PASS、证据完整；否则不是 N01 通过。

## 13. G10：第二台车 N02，不允许只改名字

当前 `joint_world_nav_io.py` 有拒绝 AMR2 的限制，`joint_nav_worker.py` 与部分 bridge 的 `/cmd_vel`/帧/车轮名字硬编码需要逐项审查。

先建立车辆注册数据：robot ID、轮关节/执行器、scan/odom/base 帧、cmd topic、action namespace、机构关节、deck ID、独立 permit。依据模型名字绑定，不复制数组索引。

两台 ROS 导航进程可以存在；**物理世界只能一个**。同一个 `/clock`。TF 的 frame ID 需要显式区分，ROS namespace 本身不会自动修正所有 TF 名字。

每车唯一 actuator 写入者；命令必须经历该车的安全链和 collision monitor。测试 AMR1 的消息不能驱动 AMR2，反之亦然；旧 callback/错误车 ID 被拒绝。

先 AMR2 孤立空载导航，再候选机构带载资格，最后它独立跑真实订单 N02。之后同世界两车在线但先不竞争，验证命令和观察无串线。

## 14. G11：真实第二托盘与有限库存

这是较大的物理缺口，不是加一个队列计数器即可。

世界开始就要有两只可区分、可达的真实空托盘，以及满足两订单的有限真实零件。H 第二次必须从真实位置取第二盘；不能 runtime 生成盘、复制物体、把第一盘瞬移回源端。

托盘架/摆位属于候选场景变更，保留旧资产并复查 H 视线、可达、自交和共享区。有限库存是 V1；无限补料与空盘循环是 V1.1，不要顺手做。

两订单必须不同，建议在最多三格的范围内选不同合法 BOM；例如一单 2 红 1 蓝、另一单 1 红 1 蓝。是否可用需以真实 schema/感知/格位能力核对，不能先硬编码成规范。

感知核数读取实际图像，不从订单倒推“应该看到几个”。库存预留、扣减与物理取件分别有证据；失败重试不重复扣账。

N03：两不同订单完成且身份/内容不混。N08：刚好两订单的库存完成后，第三单不得凭空出现材料或被错误接受。

## 15. G12：双托盘接收缓冲

已经有双槽几何不等于可用缓冲区。

定义两个实物位置、容量与占用观察、推进/停车机构或输送动作、取证条件。第一盘进入后实际移动到可保留位置，使第二入口具备净距；不删除/隐藏第一盘。

先单盘接收与定位，再第一槽占用的第二盘接收，最后满载拒绝第三盘。各盘位置/身份与 ledger 一致，接收区域资源只有实际安全时才释放。

若现有机构不能让第一盘离开入口，需要新增真实可控机构候选并重新验收，不是把 buffer_count 设成 2。

## 16. G13：车队竞争与进展性

先整理资源图：供盘区、装盘区、源端停靠/交接区、窄路、接收停靠区、接收槽、车辆任务、库存预留。

采用可解释的有限队列/优先序，不需要强化学习或 LLM。避免先占 A 再等 B、另一车先占 B 再等 A 的循环等待。等待点必须是已标定、物理可停且不堵其他路径的真实位置。

lease 用 monotonic wall time；物理动作/运动用 sim time。lease 过期并不证明区域清空。持载、半转移、车停在交接区时必须保留阻塞状态。

N04：两车竞争源端，两订单最终都完成，不能永远饿死一车。N05：窄路/接收竞争有可测进展，不靠穿车、碰撞关闭或瞬移让行。

记录排队时间、资源授予/释放、实际占用、让行动作、超时与原因。失败也要给出可判读的死锁/饥饿/导航/物理分类。

## 17. G14：电量和取消只做 V1 必需范围

仿真电量模型是声明的状态模型，不假装已验证真电池。分配前低电量选择合格车辆或拒绝；持载低电量不得简单取消后松手。

载荷途中处理：若已验证可安全完成当前接收动作则按规则继续；否则受控停止，保留载荷与资源，NEEDS_ATTENTION。自动充电不是 V1 必需，别因此新增充电项目。

取消按阶段处理：尚未取件可释放预留；抓持/半交接/运输/半卸盘必须按各阶段的物理恢复契约处理。取消 ACK 不代表资源可以释放。

## 18. G15：验收矩阵与故障要求

先逐个开发验证，再冻结正式矩阵。已有纯核心故障测试可以复用，但有物理效应的场景不能只用 mock 代替。

### 18.1 八个正常类

- N01：AMR1 完整真实订单。
- N02：AMR2 完整真实订单，无 AMR1 硬编码替身。
- N03：两个不同订单顺序执行，无身份/内容混淆。
- N04：双车源端竞争，两订单完成。
- N05：窄路/接收区竞争，有进展无死锁。
- N06：合法初始零件位置扰动，依实际视觉完成。
- N07：合法停靠扰动，重新对齐并完成真实交接。
- N08：有限库存刚好两单，额外需求诚实拒绝。

### 18.2 十二个故障类

- F01 缺零件：等待/拒绝，不造物、不猜数量。
- F02 视觉遮挡/过期：有界重观察，失败停止，不盲抓。
- F03 H 未退出共享区：臂/输送不能启动。
- F04 无托盘/接收占用：输送拒绝。
- F05 停靠超差：拒绝交接，有界重停靠。
- F06 半交接中断：双方停止，保留 TRANSFERRING 与资源。
- F07 路堵/Nav2 失败：有界恢复，无解明确停止。
- F08 分配前低电量：只选合格车或拒绝。
- F09 持载低电量：守住 custody，采用已验证安全行为或请求干预。
- F10 调度器/心跳丢失：真实受控停止，不能只有日志。
- F11 掉落/错货：独立实物验收 FAIL，区域不能假清空。
- F12 取消：阶段相关安全取消，不能自动松夹/释放区域。

### 18.3 八个基础设施类

- I01 重复命令：不重复抓取、不重复扣库存。
- I02 延迟旧 revision/boot 回调：不能结束新任务。
- I03 提交前进程退出：不双主、不无主、不虚假提交。
- I04 lease 过期：实际占用区域不释放。
- I05 验收器/安全系统离线：聚合为 UNKNOWN，不报成功。
- I06 暂停/时间回退：wall watchdog 有效，恢复需新授权。
- I07 真值依赖审计：控制/感知/导航没有货物真值捷径。
- I08 必需 FAIL/UNKNOWN/NOT_RUN：阻止总验收 PASS。

每类具体动作、判据、原始阈值以 `TEST_AND_ACCEPTANCE.md` 为准。以上是执行索引，不替换权威细则。

## 19. G16：结清 SLAM 的范围账

当前 operator-surveyed 静态地图不能称为 SLAM。原 V1 文档要求的部署建图记录必须独立完成；它不是让每个订单都在线 SLAM。

可实施路线：同世界实际 scan、odom、TF、clock → slam_toolbox 建图 → 保存 map 与元数据 → 关闭建图的 map→odom 发布者 → 独立导航启动用保存地图与定位 → 验证原导航/footprint/停靠资格。

记录 frame、sim time、scan 时间戳、地图保存/载入身份、实际建图轨迹、定位初始化、终止/重启后的可复现性。不要同时运行 AMCL 与 SLAM 抢同一 TF。

依赖若未安装或需要下载：先列缺口并请求授权，不擅自联网安装。若技术/资源不允许，只能请求用户批准发布“静态地图受限版”；未经批准，SLAM NOT_RUN 时不能宣称原始 V1 全完成。

## 20. G17–18：冻结与正式 36 实例

八正常 + 十二故障 + 八基础设施，共 28 类。N01/N04/N05/N07 各增加两个种子，共 36 实例。严格核对项目原矩阵；不能临时挑最好初态。

### 20.1 正式验收前冻结

冻结源码、候选资产、控制/相机/导航配置、地图、模型策略、依赖版本、种子、用例清单、必要阈值、判断器版本、总/阶段 wall 预算。

先跑一个代表样例确认 runner/退出/结果写入，然后按清单一个物理 worker 顺序运行。失败不删，重测用新 run ID 并说明修复版本；不能覆盖旧目录。

改代码后，受影响的用例旧报告不能继续冒充当前版本通过。说明影响集合与原因；无法证明不受影响时重跑相应集合。

### 20.2 每份报告最少包含

```text
case_id / seed / run_id / version hashes
robot_id / order_id / tray_id / transfer identities
fault injection: explicit type, phase, time, parameters
task_outcome
physical_result
safety_result
expected_behavior
evidence_complete + missing_items
simulation duration / wall duration / deadline / exit code
raw evidence paths / independent judge version
```

正常：任务 SUCCEEDED + 物理 PASS + 安全 PASS + 证据完整。

故障：任务可能 FAILED/CANCELLED/NEEDS_ATTENTION，但预期行为与安全 PASS。不能用一个总 PASS 隐去订单失败、未测分支或缺失判断。

独立验收器可读物理真值核对，但不能把该真值通过事件/共享对象送回控制器。I07 要检查完整数据流，不只搜索变量名称。

36 实例是验收集合，不是工业可靠性统计样本。不能因此宣传 99.9% 安全或真机可部署。

## 21. G19–20：真正收尾，不再无限扩展

### 21.1 独立复现

至少完整演示订单和关键故障在独立路径通过；正式要求若有更大复现集合照权威文档执行，不能临时降低。

### 21.2 文档与发布候选

公开清单排除：密钥、私人路径/身份、巨大运行缓存、无再分发许可资产、下载 token。发布候选本地整理完成不等于获准 GitHub push；推送另行请求用户。

## 23. 运行、失败和交接纪律

### 23.1 已存在的有界静止正例命令（不是移动资格）

```bash
cd ~/projects/010_heterogeneous_robot_workcell
RETAINER_RUN="p4-hinged-check-$(date -u +%Y%m%dT%H%M%S)-01"
LP_NUM_THREADS=1 .venv/bin/python scripts/run_bounded.py \
  --run-id "$RETAINER_RUN" --timeout 180 \
  experiments/probe_tray_retainer.py --hinged
```

负例使用新 ID，在末尾加 `--fault-held-release`。该注入是执行器保持释放位，不是实体机械卡死认证。

wrapper 会给 probe 加 `--run-id`，不要重复传。当前已有正负例哈希匹配时，不要求机械重复执行这两条；优先补缺失分支。

wrapper 清单在 `runtime/bounded_runs/<run-id>/manifest.json` 与 `stdout.log`；报告在 `reports/<run-id>/`。校验实际清单内容，不假定每个旧 run 字段完全一致。

### 23.2 回归与环境

物理 worker 退出后再运行完整 pytest，避免资源争抢造成假超时。示例日志名必须换成唯一的实际名称：

```bash
timeout 900 env PYTHONPATH=src:experiments LP_NUM_THREADS=1 MUJOCO_GL=egl \
  .venv/bin/python -m pytest -q > runtime/pytest-unique-change.log 2>&1
```

`source scripts/env.sh` 默认 ROS_DOMAIN_ID=43；42 属于 009，不能抢。不要在 `set -u` 下盲 source ROS setup。ROS worker 使用系统 Python；物理 worker 使用项目 venv。

不要依赖“工具响应超时”终止后台仿真。运行必须有进程级 wall 截止、PID/启动 ticks 与退出记录。重启后先核对 manifest/报告和活动进程，不能把半份日志当完成。

只能停止经核验属于本 run 的子进程，禁止 `killall`、广域 `pkill`，尤其不干扰 009。

### 23.3 每次修改前先写五行

```text
当前门：
失败的可观察原因：
这次只改变的一个因素：
预计如何反证这个修复：
运行预算、输出路径、回滚/保留方式：
```

失败分类应明确：实现缺陷、物理能力不足、观察/仪器问题、配置身份错误、无进展死锁、单纯 wall 性能预算。不得把技术失效统一叫“时间不够”。

同一假设反复失败就改测量，不盲目延长预算。已有失败如 v6 视觉遮挡、旧接触参数变体、减小步长仍不能停稳等，无新增假设不要重演。

### 23.4 每次离开时写可接手记录

- 修改文件和版本/哈希；不要只写“修好了”。
- 实际命令、run ID、wall/sim 时间、退出码。
- 原正常/负例/回归结果；未运行明确 NOT_RUN。
- 当前活动进程与归属；若退出说明已经核对。
- 哪个门已过、哪个门没过；下一步最多三项。
- 更新手写 CLAIMS 与状态源，再生成 HANDOFF；不要直接手改派生文档。

不要承诺“后台会继续”却没有运行所有权和截止。不要提交完成状态后让下一 AI 发现还缺整条链。
